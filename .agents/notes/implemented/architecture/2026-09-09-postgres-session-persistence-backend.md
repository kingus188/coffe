# Agent Note: PostgreSQL session-persistence backend

Status: implemented

## Problem

The only shipped `SessionPersistence` backend (`dsh-session-persistence-jsonl`) stores one artifact per session under a local filesystem root. A deployment that wants sessions centrally queryable, or that runs multiple application instances sharing one durable store instead of one instance owning one local disk, has no first-party backend to mount — the seam supports this (`docs/architecture.md`'s capability-seam design), but nothing shipped exercised it against a real external database.

## Decision

`dsh-session-persistence-postgres` implements the same `SessionPersistence`/`SessionHandle` contract against PostgreSQL tables (`dsh_session_header`, `dsh_session_event`, plus the derived `dsh_session_message` below) under a configurable schema. It mounts as a drop-in replacement for the JSONL backend — `agent-loop` and every other consumer are unaffected, since they depend only on the seam.

Two points diverge deliberately from JSONL parity:

- **Cross-process ownership uses a Postgres session-scoped advisory lock** (`pg_try_advisory_lock`, keyed by a hash of the session id), not a kernel file lock. This is the actual reason to choose this backend: it is the mechanism that makes single-writer-per-session hold across multiple application instances sharing one database, which a local file lock cannot do.
- **No historical format migration.** The backend writes and reads only the current `SessionEvent` format; it carries none of JSONL's v0/v1/v2 catalog, migration-preparation, or Zstandard-decode machinery. A deployment moving off JSONL starts fresh sessions here and leaves existing JSONL history on its original backend — there is no session-log migration path between the two.

Every durable write (materializing insert, event insert, header revision bump) runs in one Postgres transaction, so this backend has no torn-tail repair path: a crash mid-write leaves either the complete prior state or the complete new state, never a partial commit a reader could observe. This eliminates most of JSONL's storage-runtime complexity (byte-level materialization, `link()`-based publish, lease files, Zstandard framing) — the tables and one transaction per write replace it.

The runtime shape otherwise mirrors JSONL closely: `PostgresSessionHandle` carries the same per-handle mutation chain and bounded live-write batching window, and `PostgresBackendTracker` carries the same in-process bookkeeping (single writer per id, pending-session visibility before materialization, open-handle teardown sweep) as JSONL's `JsonlSessionHandle`/`JsonlBackendTracker`. Both backends duplicate this shape rather than sharing an implementation, matching the seam's own stated design: "each provider owns its complete storage runtime... no implementation machinery crosses the package boundary" (`dsh-session-persistence`'s package README).

### Teardown ordering across two owned resources

This backend owns a resource JSONL does not: a connection pool that must outlive every open handle's drain, then close. Cordis disposes independent top-level effects concurrently (`Promise.all` over the fiber's disposables), not in registration order — registering the pool-teardown and the handle-close sweep as two separate `ctx.effect` calls raced them, and on a fast root disposal the pool could end before a still-buffered live event's write reached the database (caught by the shared `runLiveWritePathContract` suite's "backend teardown drains buffered events through the close sweep" case). The fix: one effect that awaits `tracker.closeOpenHandles()` before calling `pool.end()`, so the ordering is explicit in the code rather than assumed from registration order.

### `header`/`event` columns are `bytea`, not `jsonb`

Postgres's `jsonb` input parser refuses any text containing a NUL byte (`unsupported Unicode escape sequence`, detail `U+0000 cannot be converted to text.`) or a lone UTF-16 surrogate (`Unicode low surrogate must follow a high surrogate.`). A real end-to-end run surfaced this: an unrelated pre-existing harness defect (a `scope` field built with a NUL byte embedded between `.` and `AGENTS.md`, from some file/workspace-scanning code) produced a session event JSONL stores without complaint but `jsonb` flatly rejects. The seam's "lossless JSON data" invariant requires this backend to store whatever `materializeCreateHeader`/`materializeAppendBatch` already validated, not re-validate it more strictly than the seam requires — so both columns store `JSON.stringify` output as raw UTF-8 bytes (`Buffer`), decoded with `JSON.parse` on read. The cost: no server-side SQL JSON querying (`->>`, `jsonb` indexes) against session content; see the package README's Known Limitations.

### `dsh_session_message`: a derived per-message table modeled on chat-product storage (e.g. ChatGPT)

The `bytea` decision above makes a session's content opaque to SQL — real friction for an operator who chose this backend specifically to make sessions "centrally queryable" and then cannot run `WHERE`/`GROUP BY`/full-text SQL against conversation content without decoding every row in application code first. A first cut added flat scalar columns (`role`, `tool_name`, `content_text`, …) directly onto `dsh_session_event`; that was reworked into a dedicated `dsh_session_message` table shaped like how a chat product stores conversation history — one row per message with a stable id, its role, and its *complete structured content* (not a flattened text summary) — because that is what "reference how a real chat product stores conversations" concretely means, and it is a materially better fit than scalar columns bolted onto the raw event log: `content` is real `jsonb` (queryable with `->>`/GIN containment, not just full-text), and the table carries the compaction-rewrite lineage (`replaces_start_seq`/`replaces_end_seq`, from the event's `surfaceOp`) a chat product's edit/regenerate history needs, which flat columns had no natural place for.

`src/derived-message.ts`'s pure `deriveMessageRow` computes one row (`message_id`, `role`, `content`, `model`/`provider`, `tool_name`/`call_id`, token-usage fields, replace lineage, `source_event_seqs`) from each event's envelope and first-party payload; `insertMessages` writes it in the *same* transaction as the row's `event` bytes, so the projection is always exactly as durable and as current as the source it derives from — no separate reconciliation pass, unlike a derived search index that observes a persistence backend from outside (`dsh-session-query-sqlite`). A generated `content_tsv tsvector` column (GIN-indexed, via `jsonb_to_tsvector`) supports full-text SQL search directly over every string leaf in `content`, without a separate flattened text column.

Only the four conversational/tool-call event types produce a row (`user/message`, `assistant/message`, `tool/call`, `tool/result`) — every other event type (todo writes, turn/step boundaries, request headers, …) is structural, not a message, and stays covered only by `dsh_session_event`'s own generic `type`/`event_time` envelope columns (added alongside this table, for querying the complete log without decoding JSON). `role` is a per-analysis value, not a verbatim copy of the wire-protocol `Message.role`: a `tool/result`'s wire role is `'user'` (its content is a user-facing tool-result block), which would make it indistinguishable from a genuine user message in a query; this table gives `tool/call`/`tool/result` their own role values instead. `content` is sanitized (`\0` → `�`, recursively through the JSON tree) before insertion — `jsonb` rejects an embedded NUL byte outright, the same class of issue that ruled out `jsonb` for `header`/`event` above — while the sibling `event` bytea column stays the untouched, lossless source; a query needing the exact original bytes still decodes `event`, never `content`.

Content extraction is implemented locally in this package rather than importing `@deepseek-ai/dsh-session-query`'s equivalent `extractSessionEventText`: that package's entrypoint is a `SessionQueryEngine` service class whose module graph pulls in session title, todo, and projection packages merely to reach one pure function, which this storage backend's minimal dependency footprint (a deliberate design point of this backend versus JSONL, see above) does not warrant paying for. This backend also needs structured content (real content blocks), not `extractSessionEventText`'s flattened searchable string.

`ensureSchema` creates `dsh_session_message` and adds `dsh_session_event`'s envelope columns via `CREATE TABLE IF NOT EXISTS`/`ADD COLUMN IF NOT EXISTS` — a schema that already exists in a deployment gains both automatically the next time any instance starts. Events appended before that upgrade have no corresponding message row; there is no backfill pass that replays pre-existing `dsh_session_event` rows into it.

## Alternatives considered

- **A shared abstract handle/tracker in the `dsh-session-persistence` seam package, extended by both backends.** Rejected: the seam package's own design principle is that providers share only the contract and the test suites, not implementation machinery, because storage runtimes differ enough (byte-level file mechanics with OS-level locks vs. SQL transactions with an advisory lock) that a shared base would need as many escape hatches as it saved lines.
- **Historical format migration parity with JSONL.** Rejected for this first cut: JSONL's migration catalog, decode/verify-in-worker pipeline, and Zstandard framing are a large fraction of its implementation and are only needed to read logs written by a retired harness version. A Postgres deployment starting fresh sessions does not need it; a future need to migrate existing JSONL history into Postgres is a distinct, separately scoped feature (an explicit import path), not a storage-format compatibility requirement of this backend.
- **A shared in-process log cache (JSONL's cold-log memo).** Rejected: it exists in JSONL to amortize file decode/decompress cost across an observe-then-resume handoff. A Postgres read is already a direct query with no decode step, so the cache would trade a small amount of latency for meaningfully more state to keep correct; deferred until a workload shows repeated large-session reads are actually expensive (see the package README's Known Limitations).
- **Cross-process ownership via `SELECT ... FOR UPDATE` row locking instead of an advisory lock.** Rejected: a row lock is transaction-scoped and would either hold a transaction open for the handle's entire lifetime (blocking autovacuum and other transactional work on the row) or need to be re-acquired per statement, losing continuous exclusion between statements. A session-scoped advisory lock held on one dedicated connection for the handle's lifetime, independent of transaction boundaries, is the mechanism Postgres documents for exactly this use.
- **`jsonb` columns for `header`/`event`.** Tried first, then reverted: `jsonb`'s stricter input parser rejects any text containing a NUL byte or a lone UTF-16 surrogate, which JSONL stores without complaint and the seam's own validation does not forbid. A real conversation run hit exactly this. `bytea` storing raw `JSON.stringify` UTF-8 bytes gives up server-side SQL JSON querying but keeps the backend's storage guarantee no stricter than the seam requires.
- **A companion `dsh-session-query-postgres` provider, mirroring `dsh-session-query-sqlite`'s externally-observing derived index.** Rejected for the scope requested: that design exists to search *live, not-yet-durable* sessions by reconciling an outside observer against a persistence backend's read handles (generation-bound cursors, connection-local TEMP-table shadowing), which this Postgres backend does not need — it already durably transacts every event within ~200ms (`LIVE_WRITE_BATCH_MAX_DELAY_MS`). Writing `dsh_session_message` inside the same transaction as the row it describes is strictly simpler and never lags its source. A full alternate query-service provider remains the right shape only if a future need requires the entire `dsh-session-query` API surface (ranked cross-session search, cursors) against Postgres specifically, not raw SQL.
- **Per-type structured columns for every `SessionEventMap` member, or a `jsonb` copy of each event's payload for `->>` queries directly on `dsh_session_event`.** Rejected: the merge-extensible event vocabulary means new plugin event types would either go unindexed (columns) or need a `jsonb` copy carrying the same NUL-byte problem `bytea` was chosen to avoid (JSON copy) on the seam's own source-of-truth table. Four event types (`user/message`, `assistant/message`, `tool/call`, `tool/result`) already cover what "analyze prior conversations" means; every other type stays structural, covered only by `dsh_session_event`'s `type`/`event_time`.
- **Flat scalar columns on `dsh_session_event` (the first cut of this feature) instead of a dedicated `dsh_session_message` table.** Reworked: a scalar `content_text` column can only hold a flattened summary, not the actual structured content (blocks, tool-call arguments as parsed data, multimodal references) a chat product's message log needs, and had no natural column for compaction-rewrite lineage (an edit/regenerate concept). A dedicated table with a `jsonb` `content` column and explicit lineage columns models this directly instead of overloading the raw event table with message-shaped columns most event types never populate.

## Consequences

Gains: a first-party path to a multi-instance-safe session store on shared Postgres, verified two ways — the full shared contract suite (`runPersistenceContract` plus `runLiveWritePathContract`, 31 cases) against a real PostgreSQL instance (Testcontainers), and a real end-to-end conversation through a production DeepSeek-API-compatible gateway, persisted to and confirmed byte-for-byte in a real externally hosted PostgreSQL database — not a mocked substitute, per the package-invariant that product-visible plugins need a non-unit real-composition test. `dsh_session_message` turns the "centrally queryable" pitch from the original decision into something an operator can actually act on with plain SQL — role/tool/token filtering, `jsonb` containment queries, full-text search, and compaction lineage — not just a shared connection string.

Costs: this backend cannot read a session written by a different harness format version, so it is not a general-purpose replacement for JSONL where operators expect the harness to keep reading old sessions across upgrades; JSONL remains the backend to choose for that guarantee. Every `read()` after a materialized open re-queries the database rather than serving from an in-process cache, which is deliberately simpler than JSONL's memo at the cost of one extra round trip per read on a hot session. The advisory lock's correctness assumption — the pooled connection holding it stays live for the handle's lifetime — is weaker than a kernel file lock's process-death guarantee: a silent network partition that drops the connection without either side observing it could let Postgres release the lock while the handle still believes it holds it; `pool.on('error', ...)` surfaces a detected failure as a warning but does not fence or retry. `bytea` storage still gives up arbitrary server-side SQL JSON querying against session content beyond what `dsh_session_message` covers (see the `jsonb`-vs-`bytea` alternative above). `content_tsv` uses the `simple` text-search configuration, which does not word-segment CJK text meaningfully; a deployment needing that installs a CJK-aware extension itself. Writing a second derived table roughly doubles this backend's per-batch insert count (one `dsh_session_event` row plus, for the four covered event types, one `dsh_session_message` row) — acceptable for a backend whose durability story is already "one transaction per batch," not a hot per-event loop.

Mounting this backend adds `pg` and this package to `dsh-base`'s own dependency closure (`apps/cli` and `packages/bundle/base` both declare it, mirroring JSONL), because `plugin-package-inventory-deepseek`'s active-package resolver locates a mounted plugin's manifest through real `node_modules` resolution, not the Loader's own tsconfig-path/source-launch resolution — a plugin reachable only through the latter (no real npm dependency edge to it from the running app) fails that resolver with `cannot resolve active package`, breaking the `dsh_plugin_packages` request extension for the whole process, not just this plugin. Every consumer of `dsh-base` now carries `pg` in its dependency closure whether or not it mounts this backend; reconsider if that footprint matters more than the parity with how JSONL is already declared.

## Testing

`packages/session/session-persistence-postgres/tests/contract.e2e.ts` starts one Postgres container (Testcontainers) for the file and runs both shared contract suites against it, each case in its own schema, plus a dedicated case that appends a structural event and one of each conversational/tool-call event type, then asserts via direct SQL that `dsh_session_event` carries every event generically (`type`/`event_time`) while `dsh_session_message` carries a row only for the four covered types, with the exact expected `role`/`content`/`model`/`tool_name`/`call_id`/token values and a `content_tsv` full-text match; it self-skips when Docker is unreachable, the same policy this repo applies to real-provider-key e2e suites. `tests/schema.spec.ts` unit-pins the pure DDL-identifier-quoting helper; `tests/derived-message.spec.ts` unit-pins `deriveMessageRow` at 100% coverage (role/content/tool/call-id/token/replace-lineage extraction per event type, NUL-byte sanitization through nested content, the merge-extensible default producing no row). Not yet covered: this package is not yet part of the mandatory `pnpm run test:coverage` per-file gate for its Postgres-driver-touching files (`index.ts`, `storage.ts`, `schema.ts`, `lock.ts` — their behavior lives behind the Docker-gated e2e suite, not the always-on unit suite); `derived-message.ts` is pure logic and does carry unit coverage. A follow-up should decide whether to bring real Postgres coverage into that gate or accept the same carve-out precedent this repo has none of yet.

Beyond the automated suites, this backend was verified once against a real externally hosted PostgreSQL instance (not Testcontainers) and a real production DeepSeek-API-compatible gateway: `dsh --profile headless` ran a real conversation with this backend mounted in place of JSONL, and the resulting session (headers and every event, including the model's actual reply text) was confirmed present and byte-correct via a direct read of the database afterward. That run is what surfaced both the `jsonb`-vs-`bytea` issue and the `plugin-package-inventory-deepseek` dependency-closure issue above; neither the contract suite nor the live-write-path suite exercises a real LLM adapter or the request-extension pipeline, so this class of integration issue is not covered by the automated suites and would recur for a similarly-shaped future backend that skips a manual full-stack run.
