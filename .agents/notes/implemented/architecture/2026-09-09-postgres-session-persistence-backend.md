# Agent Note: PostgreSQL session-persistence backend

Status: implemented

## Problem

The only shipped `SessionPersistence` backend (`dsh-session-persistence-jsonl`) stores one artifact per session under a local filesystem root. A deployment that wants sessions centrally queryable, or that runs multiple application instances sharing one durable store instead of one instance owning one local disk, has no first-party backend to mount — the seam supports this (`docs/architecture.md`'s capability-seam design), but nothing shipped exercised it against a real external database.

## Decision

`dsh-session-persistence-postgres` implements the same `SessionPersistence`/`SessionHandle` contract against two PostgreSQL tables (`dsh_session_header`, `dsh_session_event`) under a configurable schema. It mounts as a drop-in replacement for the JSONL backend — `agent-loop` and every other consumer are unaffected, since they depend only on the seam.

Two points diverge deliberately from JSONL parity:

- **Cross-process ownership uses a Postgres session-scoped advisory lock** (`pg_try_advisory_lock`, keyed by a hash of the session id), not a kernel file lock. This is the actual reason to choose this backend: it is the mechanism that makes single-writer-per-session hold across multiple application instances sharing one database, which a local file lock cannot do.
- **No historical format migration.** The backend writes and reads only the current `SessionEvent` format; it carries none of JSONL's v0/v1/v2 catalog, migration-preparation, or Zstandard-decode machinery. A deployment moving off JSONL starts fresh sessions here and leaves existing JSONL history on its original backend — there is no session-log migration path between the two.

Every durable write (materializing insert, event insert, header revision bump) runs in one Postgres transaction, so this backend has no torn-tail repair path: a crash mid-write leaves either the complete prior state or the complete new state, never a partial commit a reader could observe. This eliminates most of JSONL's storage-runtime complexity (byte-level materialization, `link()`-based publish, lease files, Zstandard framing) — the tables and one transaction per write replace it.

The runtime shape otherwise mirrors JSONL closely: `PostgresSessionHandle` carries the same per-handle mutation chain and bounded live-write batching window, and `PostgresBackendTracker` carries the same in-process bookkeeping (single writer per id, pending-session visibility before materialization, open-handle teardown sweep) as JSONL's `JsonlSessionHandle`/`JsonlBackendTracker`. Both backends duplicate this shape rather than sharing an implementation, matching the seam's own stated design: "each provider owns its complete storage runtime... no implementation machinery crosses the package boundary" (`dsh-session-persistence`'s package README).

### Teardown ordering across two owned resources

This backend owns a resource JSONL does not: a connection pool that must outlive every open handle's drain, then close. Cordis disposes independent top-level effects concurrently (`Promise.all` over the fiber's disposables), not in registration order — registering the pool-teardown and the handle-close sweep as two separate `ctx.effect` calls raced them, and on a fast root disposal the pool could end before a still-buffered live event's write reached the database (caught by the shared `runLiveWritePathContract` suite's "backend teardown drains buffered events through the close sweep" case). The fix: one effect that awaits `tracker.closeOpenHandles()` before calling `pool.end()`, so the ordering is explicit in the code rather than assumed from registration order.

### `header`/`event` columns are `bytea`, not `jsonb`

Postgres's `jsonb` input parser refuses any text containing a NUL byte (`unsupported Unicode escape sequence`, detail `U+0000 cannot be converted to text.`) or a lone UTF-16 surrogate (`Unicode low surrogate must follow a high surrogate.`). A real end-to-end run surfaced this: an unrelated pre-existing harness defect (a `scope` field built with a NUL byte embedded between `.` and `AGENTS.md`, from some file/workspace-scanning code) produced a session event JSONL stores without complaint but `jsonb` flatly rejects. The seam's "lossless JSON data" invariant requires this backend to store whatever `materializeCreateHeader`/`materializeAppendBatch` already validated, not re-validate it more strictly than the seam requires — so both columns store `JSON.stringify` output as raw UTF-8 bytes (`Buffer`), decoded with `JSON.parse` on read. The cost: no server-side SQL JSON querying (`->>`, `jsonb` indexes) against session content; see the package README's Known Limitations.

## Alternatives considered

- **A shared abstract handle/tracker in the `dsh-session-persistence` seam package, extended by both backends.** Rejected: the seam package's own design principle is that providers share only the contract and the test suites, not implementation machinery, because storage runtimes differ enough (byte-level file mechanics with OS-level locks vs. SQL transactions with an advisory lock) that a shared base would need as many escape hatches as it saved lines.
- **Historical format migration parity with JSONL.** Rejected for this first cut: JSONL's migration catalog, decode/verify-in-worker pipeline, and Zstandard framing are a large fraction of its implementation and are only needed to read logs written by a retired harness version. A Postgres deployment starting fresh sessions does not need it; a future need to migrate existing JSONL history into Postgres is a distinct, separately scoped feature (an explicit import path), not a storage-format compatibility requirement of this backend.
- **A shared in-process log cache (JSONL's cold-log memo).** Rejected: it exists in JSONL to amortize file decode/decompress cost across an observe-then-resume handoff. A Postgres read is already a direct query with no decode step, so the cache would trade a small amount of latency for meaningfully more state to keep correct; deferred until a workload shows repeated large-session reads are actually expensive (see the package README's Known Limitations).
- **Cross-process ownership via `SELECT ... FOR UPDATE` row locking instead of an advisory lock.** Rejected: a row lock is transaction-scoped and would either hold a transaction open for the handle's entire lifetime (blocking autovacuum and other transactional work on the row) or need to be re-acquired per statement, losing continuous exclusion between statements. A session-scoped advisory lock held on one dedicated connection for the handle's lifetime, independent of transaction boundaries, is the mechanism Postgres documents for exactly this use.
- **`jsonb` columns for `header`/`event`.** Tried first, then reverted: `jsonb`'s stricter input parser rejects any text containing a NUL byte or a lone UTF-16 surrogate, which JSONL stores without complaint and the seam's own validation does not forbid. A real conversation run hit exactly this. `bytea` storing raw `JSON.stringify` UTF-8 bytes gives up server-side SQL JSON querying but keeps the backend's storage guarantee no stricter than the seam requires.

## Consequences

Gains: a first-party path to a multi-instance-safe session store on shared Postgres, verified two ways — the full shared contract suite (`runPersistenceContract` plus `runLiveWritePathContract`, 31 cases) against a real PostgreSQL instance (Testcontainers), and a real end-to-end conversation through a production DeepSeek-API-compatible gateway, persisted to and confirmed byte-for-byte in a real externally hosted PostgreSQL database — not a mocked substitute, per the package-invariant that product-visible plugins need a non-unit real-composition test.

Costs: this backend cannot read a session written by a different harness format version, so it is not a general-purpose replacement for JSONL where operators expect the harness to keep reading old sessions across upgrades; JSONL remains the backend to choose for that guarantee. Every `read()` after a materialized open re-queries the database rather than serving from an in-process cache, which is deliberately simpler than JSONL's memo at the cost of one extra round trip per read on a hot session. The advisory lock's correctness assumption — the pooled connection holding it stays live for the handle's lifetime — is weaker than a kernel file lock's process-death guarantee: a silent network partition that drops the connection without either side observing it could let Postgres release the lock while the handle still believes it holds it; `pool.on('error', ...)` surfaces a detected failure as a warning but does not fence or retry. `bytea` storage gives up server-side SQL JSON querying against session content (see the `jsonb`-vs-`bytea` alternative above).

Mounting this backend adds `pg` and this package to `dsh-base`'s own dependency closure (`apps/cli` and `packages/bundle/base` both declare it, mirroring JSONL), because `plugin-package-inventory-deepseek`'s active-package resolver locates a mounted plugin's manifest through real `node_modules` resolution, not the Loader's own tsconfig-path/source-launch resolution — a plugin reachable only through the latter (no real npm dependency edge to it from the running app) fails that resolver with `cannot resolve active package`, breaking the `dsh_plugin_packages` request extension for the whole process, not just this plugin. Every consumer of `dsh-base` now carries `pg` in its dependency closure whether or not it mounts this backend; reconsider if that footprint matters more than the parity with how JSONL is already declared.

## Testing

`packages/session/session-persistence-postgres/tests/contract.e2e.ts` starts one Postgres container (Testcontainers) for the file and runs both shared contract suites against it, each case in its own schema; it self-skips when Docker is unreachable, the same policy this repo applies to real-provider-key e2e suites. `tests/schema.spec.ts` unit-pins the pure DDL-identifier-quoting helper. Not yet covered: this package is not yet part of the mandatory `pnpm run test:coverage` per-file gate (its behavior lives behind the Docker-gated e2e suite, not the always-on unit suite) — a follow-up should decide whether to bring real Postgres coverage into that gate or accept the same carve-out precedent this repo has none of yet.

Beyond the automated suites, this backend was verified once against a real externally hosted PostgreSQL instance (not Testcontainers) and a real production DeepSeek-API-compatible gateway: `dsh --profile headless` ran a real conversation with this backend mounted in place of JSONL, and the resulting session (headers and every event, including the model's actual reply text) was confirmed present and byte-correct via a direct read of the database afterward. That run is what surfaced both the `jsonb`-vs-`bytea` issue and the `plugin-package-inventory-deepseek` dependency-closure issue above; neither the contract suite nor the live-write-path suite exercises a real LLM adapter or the request-extension pipeline, so this class of integration issue is not covered by the automated suites and would recur for a similarly-shaped future backend that skips a manual full-stack run.
